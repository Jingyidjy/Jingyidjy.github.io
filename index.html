01 — 架构

一个 Agent，四种入口

对用户来说产品叫 Grok，只有一个。底层却是一套「协议优先于界面」的结构：agent 核心只认 ACP（JSON-RPC），前端只是决定字节从哪条路走。

TUI  ·  编辑器  ·  脚本  ·  浏览器
 │        │        │        │
 ├ 进程内线程            ← 默认快路径，无 IPC
 ├ stdio（JSON-RPC）    ← Zed / Neovim / SDK
 ├ Unix socket        ← ~/.grok/leader.sock
 │   └─ leader 守护进程：一个 agent，多客户端
 │     请求 ID 加 client_id| 前缀，避免并发串味
 └ WebSocket           ← agent serve / 云端中继
        │
        ▼
   ┌──────────────────────────────────┐
   │  MvpAgent  ── 会话 ── 回合 ── 工具 │
   └──────────────────────────────────┘

图 1 — 四种驱动方式共用同一个核心；实体线是数据传输层，不是进程边界。

四种入口
入口给谁用传输
grok人，交互式进程内线程，或连本机 leader
agent stdio编辑器、SDK、评测脚本标准输入输出的 JSON-RPC
-p "…"CI、脚本一次性提示，退出

有一个很产品化的取舍：一旦开启 OS 沙箱（macOS seatbelt / Linux landlock），leader 模式会被禁用。因为工具必须在进程内跑才待得住沙箱。要么共享，要么隔离，不能既要又要。

02 — 回合

提交不是发送，是入队

用户按下 Enter 之后，发生的第一件事不是调用模型，而是把消息放进一个由服务端掌管事实的队列。

这是多客户端设计逼出来的：终端和 IDE 可能同时看着同一个会话，队列状态不能各排各的。客户端只画一条乐观回显，等服务端广播 x.ai/queue/changed 回来再确认。

随后一轮回合展开，每个工具动作都不是黑箱——它在对话流里占一个可折叠条目，带 inline diff、命令输出、失败原因，完成时原地更新。产品没有把 Agent 包装成问答机器人，而是把它呈现成一份可回放的工作日志：你随时能滚回去看它为什么改了那行代码。

回合结束的原因，分了七种

正常结束、被取消、模型拒答、限流、错误、超 token、超工具次数、被中断——这些对应的是完全不同的收尾界面：限流要提示等待，超 token 要建议压缩上下文，被 hook 拦截要说明理由。它们不该都显示成「出错了」。

03 — 打断

三种意图，不合并成一个「取消」

多数工具把打断做成一个按钮。Grok 拆成了三档，而且刻意不让你误触。

排队 Enter

回合运行中按普通 Enter，消息进队列，当前回合跑完再跑。不打断，也不丢。

插话 interject

不打断正在做的事，把补充注入到下一个安全间隙。「顺便把测试也加了」不需要杀进程。

立刻停 Ctrl+Enter

停掉当前回合，把这条作为下一回合发出。真正的「换方向」。

回退 / 分叉 /rewind · /fork

回合之后的操作，和打断正交。前者退回去重来，后者保留历史走另一条路。

按键语义也被认真区分过：Esc 永远不杀回合，中途按只提示你去用 Ctrl+C；Ctrl+C 在输入框有草稿时第一次只清草稿，第二次才真取消。空稿双击 Esc 是回退。这三件事砸到同一个键上，是很多工具让人不敢按 Esc 的原因。

04 — 等待

Agent 等人时的四种卡片

交互的关键不是「发消息」，而是当 Agent 停下来等你时，界面怎么保证你既不迷路、也不丢东西。

Grok 明确定义了四种会接管键盘的阻塞界面，并给它们一条统一的键盘契约：Tab 只在卡内循环、绝不逃出去；Esc 是一格一格往回退而不是粗暴关闭；退到底会把键盘「停在对话流」上让你翻上下文，卡片仍留在屏上，底部提示会写着 Tab/Space: question 把你带回来。

同时打开时的优先级
顺序卡片它问什么
1权限审批这条命令 / 这个文件改动，准不准
2取消回合面板多个子 Agent 在跑，停哪些
3提问卡Agent 主动问你，可多选、可自由填写
4MCP 征询卡外部服务器要表单或 URL 授权
「用户没看见」不等于「用户拒绝」。后台 Agent 的提问不会因为当时没人在看就被判失败。 ask_user_question 的悬停设计

这条最见功力。在多会话并行时，后台会话发来的提问如果找不到归属视图，代码故意不返回错误，而是让请求悬着，等客户端接上后由 leader 重放。否则多 Agent 协作会不断因为「没人看」而莫名其妙地失败。

05 — 信任

一次工具调用，过五道闸

信任不是一次开关，是逐步下放的。顺序固定，规则先于模式。

  1. PreToolUse hook用户自己的代码可否决；但它放行不代表跳过后面几道。
  2. 权限规则deny > ask > allow，按项目作用域。
  3. 已记住的授权「这条命令以后都行」沉下来，不必反复问。
  4. 只读白名单读文件、git log、rg 等自动放行；shell 按 &&、| 分段逐段判定。
  5. 模式策略默认问 / acceptEdits / auto（分类器先判，拿不准再弹） / dontAsk / always-approve。

审批弹窗里不只有是 / 否。你可以顺手塞一句话回给模型——「可以，但用 pnpm」。这是把「批准」和「纠偏」合并成一个动作。

Plan mode 是硬边界，不是提示词

进入后除 plan.md 外一切写入都会被直接拒绝，连 always-approve 也破不了例。Agent 自己觉得任务有歧义时能申请进入，但要用户点头；收尾时把计划摊开供你逐行评论、批准或打回。结构性的不可逆操作，用结构性的机制来拦。

沙箱是第二层：权限决定「准不准干」，沙箱决定「干了也出不去」。

06 — 扩展

人还能往回路里插代码

Hooks 不只是拦截器，它能改写 Agent 看到的世界。

Stop hook 可以阻止回合结束并把理由喂回去——「测试还没过，继续」。PostToolUse 可以改写模型看到的工具输出（脱敏、截断），而真实结果仍留在日志里。Skills 按项目 → 仓库 → 用户逐层发现，并且同时扫描 ~/.claude/skills 和 ~/.cursor/skills。

最后这点是明确的产品策略：让你从别家迁移过来时，手上那套技能直接能用。工具层里甚至同时存在从 openai/codex 和 sst/opencode 移植的实现，并提供多套「工具命名空间」——同一能力，多种话术，按模型配置选。兼容做到了提示层。

07 — 结论

它到底怎么理解「人机交互」

  • Agent 不是聊天对象，是一个可审计的执行者。所以一切流式可见、可折叠、可复制、可回放。
  • 人是监督者，不是操作员。所以默认问、逐步放权、有只读白名单、有分类器、有逃生门。
  • 打断是三种意图，不是一种。停止、插话、回退各归各，按键也不共用一个。
  • Agent 等人的那几秒决定体验。所以四种卡片共用一套键盘契约，Esc 永远不丢东西。
  • 协议优先于界面。真正被产品化的是 agent 核心，终端界面只是众多前端之一。
  • 迁移摩擦要主动消除。兼容别家的 skills 与工具实现，是为了让人不必因为换工具而重学一套。
